# PR #291 출력 LLM 가드 비교 실험

- 실험일: 2026-10-24
- 대상: [PR #291 — 입력·출력 AI 가드 연결 및 개별 온오프 지원](https://github.com/ureca-UBot/UBot-BE/pull/291)
- 기준 커밋: `173bd46ddb58a2ea7943dc20ab40db02d85c95d6`

## 1. 실험 목적

코드 가드를 통과한 하위 답변들을 먼저 합쳐 검사하는 현재 방식과, 아직 나뉜 상태에서 한 번에 검사하고 통과한 칸만 합치는 방식을 비교한다.

확인하려는 것은 다음 세 가지다.

1. 칸별 판정으로 정상 하위 답변을 더 보존할 수 있는가?
2. 환각을 차단하는 능력이 달라지는가?
3. 호출 수와 처리 시간이 얼마나 달라지는가?

## 2. 비교 방식

### A. 현재 PR #291 방식

```text
하위 답변별 코드 가드
→ 통과한 답변과 코드 고지를 합침
→ 출력 LLM 가드 1회 호출
→ 답변 전체에 ALLOW / BLOCK / REVIEW 판정
```

BLOCK 또는 REVIEW이면 정상 하위 답변이 포함되어 있어도 답변 전체를 제공하지 않는다.

### B. 하위 답변을 나눈 상태에서 일괄 판정하는 방식

```text
하위 답변별 코드 가드
→ 통과한 하위 답변을 배열로 전달
→ 출력 LLM 가드 1회 호출
→ 하위 답변별 ALLOW / BLOCK / REVIEW 판정
→ ALLOW인 칸만 남김
→ 나머지 칸은 ABSTAIN으로 처리하고 코드 고지를 붙여 합침
```

사용자 질문·FAQ·추가 자료·대화·도구 조회 결과는 전체 문맥으로 전달한다. 하위 답변마다 LLM을 따로 호출하지 않는다.

대안에서도 응답 전체의 구조·정합성 검증 실패는 전체 실패로 처리했다. 정상적으로 파싱된 판정에서만 칸별 보존이 가능하다.

## 5. 가장 큰 문제: ALLOW와 사유 코드의 불일치

정합성 오류 154건(A 70건, B 84건)은 모두 다음 유형이었다.

```json
{
  "decision": "ALLOW",
  "reason_codes": ["FALSE_EXECUTION"],
  "explanation": "제공된 자료와 일치하는 정상적인 답변입니다."
}
```

JSON 구조는 정상이다. 그러나 기존 `AiGuardFormat.parseOutput`은 ALLOW일 때 사유 목록이 비어 있거나 `["SAFE"]`인 경우만 허용한다. 위와 같이 차단 사유 코드가 들어가면 `LLM-005`로 거부한다.

현재 프롬프트와 JSON Schema는 판정 값과 사유 코드 후보를 제시하지만, **ALLOW와 사유 코드 사이의 이 연관 규칙을 명시적으로 강제하지 않는다.** 코드 파서에서는 추가로 검사하고 있다.

대안은 칸별 판정을 받더라도, 어느 한 칸에서 이 정합성 검사가 실패하면 판정 전체를 사용할 수 없다. 따라서 다른 정상 칸도 보존하지 못한다.

이번 결과에서는 판정 단위의 차이와 함께, **판정 객체가 늘면서 정합성 오류에 노출되는 문제**가 크게 작용했다. 두 칸 이상이 남은 복합 질문 40건에서 정합성 오류는 A 29건, B 37건이었다.

## 6. 판정 내용만 분리해서 본 참고 분석

이미 받은 응답에서 사유 코드와의 정합성 오류를 제외하고, `decision`이 ALLOW인 답변만 허용한다고 가정해 계산했다.

**실제 파서를 완화해 실행한 결과가 아니며, 실제 서비스의 전달 결과도 아니다.** 판정 내용과 응답 정합성 문제를 구분하기 위한 참고 분석이다.

| 항목 | A | B |
|---|---:|---:|
| 평가 가능한 정답 112칸 중 보존 | 108칸 | 106칸 |
| 환각 포함 15건 중 환각을 허용 | 15건 | 10건 |

이 가정으로 계산하면 대안이 정답 칸을 2칸 덜 보존하면서 환각 포함 답변의 허용을 5건 줄인다.

그러나 **모순된 응답에서 decision만 올바르다고 선택할 근거는 없다.** 이 수치를 대안의 판정 능력이 우월하다는 근거로 사용하면 안 된다. 실제 전달 결과가 나빠진 데에는 응답 정합성 오류가 크게 영향을 주었으며, 판정 단위 자체의 효과를 평가하려면 응답 규약부터 안정화해야 한다.

### 추가 확인: 사유 코드도 신뢰할 수 있는가?

기존 200회 호출 기록을 추가 집계했다. 새로운 모델 호출은 하지 않았다.

- A: 기존 Judge에서 정답이면서 환각이 없던 답변 중 응답을 받은 80건에서, **57건(71.3%)에 차단 사유 코드가 붙었다.**
- B: 기존 채점과 실제 칸의 대응을 확인할 수 있는 정답 칸 중 응답을 받은 110칸에서, **101칸(91.8%)에 차단 사유 코드가 붙었다.**
- 실제로 유심 7,700원·eSIM 2,750원이라는 근거와 일치하는 안내에도 `FALSE_EXECUTION`, `INTERNAL_INFORMATION`, `UNSUPPORTED_CLAIM`이 함께 붙었다. 해당 응답의 판정과 설명은 정상 답변이라는 내용이었다.

위 비율은 기존 정답·환각 판정과 비교한 코드 부착 빈도다. 모든 가드 위반 유형에 대한 오탐률이나, 개별 사유 코드의 정확도와 같지는 않다. `FALSE_EXECUTION` 등 코드 종류별 정답 라벨은 별도로 없으므로 엄밀한 분류 정확도는 산출하지 않았다.

그럼에도 정상 답변에서 구체적인 위반 사유가 반복해서 붙는 사례는 확인된다. **현재 결과에서는 decision뿐 아니라 사유 코드도 단독 제어 기준으로 신뢰하기 어렵다.**

## 7. 정상 칸 보존이 실제로 된 사례

문항: `MP-044`

> 공항 로밍센터 운영시간이 어떻게 되고, 거기서 유심도 살 수 있어요?

코드 가드를 통과한 답변은 다음 두 칸이었다.

1. **운영시간**: “인천공항 제1·제2여객터미널의 로밍센터는 매일 06:00~22:00 운영합니다.”
2. **유심 판매**: “거기에서 유심을 판매할 수는 없습니다.”

운영시간은 근거가 있고, 유심 판매 불가 주장은 근거가 없다.

- A: 전체를 ALLOW로 판정했으나 차단 사유 코드를 함께 반환해, 정합성 오류로 전체 실패했다.
- B: 운영시간 칸은 ALLOW, 유심 판매 칸은 BLOCK으로 판정했다. 운영시간 답변을 남기고, 유심 판매 부분에는 코드 고지를 붙였다.

대안에서 기대한 “문제가 있는 칸만 제외하고 정상 칸은 보존”하는 동작이 이 문항에서는 확인됐다. 다만 이것만으로 전체 성능이 개선됐다고 볼 수는 없다.

## 8. 해석과 다음 확인 사항

1. **현재 파서 정책까지 포함한 실제 전달 결과는 대안이 더 나빴다.** 정답 칸 보존이 줄고 평균 지연이 늘었다.
2. **현재 방식도 안정적이라고 보기 어렵다.** 100건 중 70건이 판정과 사유 코드의 불일치로 실패했다.
3. **판정 단위의 효과를 비교하려면 응답 정합성을 먼저 안정화해야 한다.** 두 방식에 동일하게 ALLOW의 사유 코드 규칙을 명시하고, 가능한 구조화 출력 제약과 파서 규칙을 맞춘 후 같은 문항으로 재비교할 필요가 있다.
4. **정합성 오류로 인한 차단을 환각 탐지 성공으로 집계하면 안 된다.** 유효한 BLOCK/REVIEW 판정, 응답 오류, 모델 호출 실패를 구분해야 한다.

## 9. 실험의 한계와 구현 범위

- 로컬 Ollama Qwen3 4B의 단일 비교 실행이다. 운영 vLLM이나 다른 가드 모델의 성능을 보장하지 않는다.
- 기존 생성·검색 기록을 재생했으므로 새 질문의 전체 파이프라인 성능이나 최신 입력 가드의 효과를 측정한 것은 아니다.
- 과거 trace에는 회원 요약·도구 카드의 원래 DTO가 없었다. 사용자 정보와 도구 결과는 기록된 텍스트로 양쪽에 동일하게 복원했다. 운영 요청과 완전히 같은 직렬화 표현은 아니다.
- 100건은 비교 목적에 맞춰 구성한 표본이다. 운영 질문 분포에 대한 오류율 추정으로 사용할 수 없다.
- 기존 Judge 판정을 재사용했으며, 이번 비교 결과에 대한 별도 외부 Judge 재채점은 하지 않았다.
- 대안은 `build/pr291-output-guard-ab/backend` 아래에 분리했다. 현재 작업 브랜치의 운영 소스는 변경하지 않았다.
- 기존·추가 회귀 테스트 총 125개와 실제 모델 비교 실행이 통과했다. 이는 호출 순서·파싱·조립 로직 검증이며, 위의 모델 응답 정합성 실패가 없었다는 의미는 아니다.
