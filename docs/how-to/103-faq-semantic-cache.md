# 공식 FAQ 시맨틱 캐시 사용 안내

관리자가 승인한 일반 안내 FAQ에 등록 질문 표현을 연결하고, 사용자 질문이 조건을 통과하면 공식 답변을 직접 반환해요. 추가 추론 모델은 사용하지 않아요.

**기본값은 OFF예요.** 기존 실험에서 의도·조건이 다른 질문을 통과시킨 사례가 있어요. 일부 질문이 잘 동작한다는 결과만으로 전체 질문에 안전하다고 판단하지 않아요.

## 1. 설정

환경변수 전체 설명은 [설정 안내](../reference/configuration.md)에 있어요.

```properties
FAQ_CACHE_ENABLED=false
FAQ_CACHE_SEMANTIC_ENABLED=false
FAQ_CACHE_MIN_SIMILARITY=0.95
FAQ_CACHE_MIN_MARGIN=0.15
```

캐시를 사용하려면 `FAQ_CACHE_ENABLED`와 `FAQ_CACHE_SEMANTIC_ENABLED`를 true로 설정하고 백엔드를 다시 시작한다. 관리자가 승인한 활성 GENERAL FAQ에 유효한 표현을 등록하면 검색·판정 대상이 된다. FAQ ID나 승인 FAQ 개수를 코드에 고정하지 않는다.

모든 대상 FAQ에 공통 `FAQ_CACHE_MIN_SIMILARITY`와 `FAQ_CACHE_MIN_MARGIN`을 적용한다. 기존 5개 FAQ 전용 검토 정책과 `FAQ_CACHE_REVIEWED_POLICY_ENABLED` 설정은 제거했다. 해당 정책으로 측정한 과거 HIT율·응답 시간은 현재 구성의 검증 결과가 아니다. 캐시 검색과 표현 등록은 채팅과 같은 `EmbeddingService`·`EmbeddingProfileService`를 사용한다. Ollama는 `OLLAMA_EMBEDDING_MODEL`, vLLM은 `EMBEDDING_MODEL`을 사용하며 별도 `FAQ_CACHE_EMBEDDING_MODEL` 설정은 사용하지 않는다. provider·모델·차원·프로필 버전이 달라지면 벡터를 공유하지 않으며 기준을 다시 검증해야 한다.

## 2. 처리 흐름

1. 기존 FAQ 검색은 질문 원문을 현재 임베딩 프로필로 임베딩해요. 캐시 검색에는 NFC·공백·반복 물음표/느낌표를 정리한 질문을 사용해요. 두 입력이 같으면 벡터를 재사용하고, 달라지면 같은 모델로 캐시용 임베딩을 추가로 만들어요. 질문 이력과 LLM에 전달할 원문은 유지해요.
2. 기존 FAQ Top 3와 시맨틱 후보 20개를 검색해요. 동일 FAQ의 여러 표현은 최고 점수로 묶고, 승인되지 않은 FAQ도 경쟁 후보로 남겨요. 추가 임베딩이나 시맨틱 조회 실패 시 이미 검색한 원문 FAQ 결과를 사용해요.
3. 승인된 활성 GENERAL FAQ인지, 등록 표현과 공식 내용·버전·프로필이 일치하는지, 질문 범위·유사도·경쟁 점수 차이가 기준을 통과하는지 확인해요.
4. 통과한 FAQ는 DB의 최신 승인과 질문·답변·버전을 다시 확인해요.
5. 검증된 DB의 공식 답변을 직접 반환하고 LLM 호출을 생략해요. FAQ 답변은 Redis에 저장하거나 조회하지 않아요.

이전 버전의 `faq:answer:*` Redis 키는 현재 흐름에서 사용하지 않으며 기존 TTL에 따라 만료돼요. `FAQ_CACHE_TTL` 설정도 더 이상 사용하지 않아요. 랭킹 등 다른 기능의 Redis 사용은 유지해요.

추가 검색 실패·판정 거절·DB 검증 실패면 공식 답변을 생략하고 기존 처리 경로를 사용해요. 기존 FAQ 검색 자체가 실패하면 기존 오류 처리를 따르고, 현재 프로필의 벡터가 없으면 다른 프로필로 대체 검색하지 않아요. 기존 FAQ의 근거 기준은 Top 3 / 0.75예요. 기준 미달 질문은 LLM을 호출하지 않고 미응답으로 끝날 수 있어요. 사용자 intent를 지정한 재검색에는 캐시를 적용하지 않아요.

## 3. DB 준비

| 마이그레이션 | 역할 |
|---|---|
| V28 | FAQ와 수정 이력에 `cacheable` 추가. 기본 false |
| V29 | 임베딩 프로필별 등록 표현, 고정 공식 내용·버전, 정규화 키·버전 및 유니크 제약을 포함한 테이블 생성 |

V29에서 `normalized_question`을 DB 생성 컬럼으로 만들고, 같은 FAQ·프로필의 정규화된 질문이 중복 저장되지 않도록 해요. Java API는 정규화된 입력을 실제로 임베딩한 뒤 `normalization_version=1`로 등록해요. 정규화 버전을 명시하지 않은 직접 입력은 기본값 0이며 캐시 검색에서 제외돼요. 마이그레이션은 모델을 호출하지 않아요.

병합 전 마이그레이션을 V29에 통합했으므로, 이전 V29를 이미 적용한 로컬 DB는 체크섬이 달라져 그대로 재시작할 수 없어요. 데이터 보존이 필요하면 먼저 백업하고 별도 새 로컬 DB에 최신 마이그레이션을 적용해요. 기존 DB는 자동으로 초기화하지 않아요.

마이그레이션은 FAQ 승인이나 표현 등록을 자동으로 하지 않아요. FAQ와 현재 프로필의 질문 벡터는 [로컬 데이터 안내](local-data.md)와 [임베딩 백필 안내](llm-module.md#백필)를 참고해 준비해요.

**이전 실험 DB에 이 브랜치를 그대로 연결하면 안 돼요.** 이전 실험은 V25/V26을 캐시에 사용했고, 최신 develop은 같은 번호를 legacy 벡터 제거·가입 정보 테이블에 사용해요. 별도 DB에 최신 마이그레이션을 적용해야 해요. 기존 DB 이력을 repair하거나 체크섬을 바꿔서 맞추지 않아요.

## 4. 관리자 승인

`POST /admin/faqs`, `PATCH /admin/faqs`의 `cacheable` 필드로 승인해요.

- 생성 시 생략하면 false예요.
- 수정 시 생략하면 기존 GENERAL FAQ의 승인 상태를 유지해요.
- intent를 USER_DATA/STORE_DATA로 바꾸면 생략된 승인은 해제돼요.
- GENERAL이 아닌 FAQ에 true를 명시하면 `FAQ-007`로 거절해요.
- 승인 변경은 수정 이력에 남고 FAQ 버전이 올라가요.

PATCH에는 id·categoryId·question·answer·intent 등 기존 필수 필드도 보내야 해요. FAQ 내용·버전이 바뀌면 과거 표현은 검색에서 제외돼요. 다시 검토해 등록해야 해요.

## 5. 표현 등록·조회·비활성화

운영에서 표현은 Java 관리자 API로 관리해요. Python 프로세스를 실행할 필요는 없어요. `/admin/**`의 기존 관리자 인증을 사용해요.

`FaqCacheQuestion` 엔티티가 표현·프로필 ID·정규화 키/버전·1024차원 벡터·FAQ 내용/버전·활성 상태·생성 시각을 매핑해요. 정규화 키와 생성 시각은 DB가 계산해요. 표현 비활성화는 엔티티 기반 JPQL로 처리하고, 원자적 upsert와 벡터 검색·유효 상태 조회에는 SQL을 사용해요.

| API | 역할 |
|---|---|
| `POST /admin/faqs/{faqId}/cache-questions` | 현재 프로필로 표현을 임베딩해 추가·갱신 |
| `GET /admin/faqs/{faqId}/cache-questions` | 해당 FAQ의 모든 프로필 표현과 유효 상태 조회 |
| `DELETE /admin/faqs/{faqId}/cache-questions/{questionId}` | 표현 한 개를 `enabled=false`로 비활성화 |

등록 요청 예시:

```json
{
  "questions": [
    "esim이 뭐야?",
    "esim이 어떤 건지 설명해줘."
  ]
}
```

FAQ가 활성 GENERAL이고 `cacheable=true`이며, 현재 프로필의 질문 벡터가 있어야 등록할 수 있어요. 한 번에 최대 50개, 표현 하나는 최대 160자예요. NFC, 공백·탭·NBSP·전각 공백, 반복 물음표와 느낌표를 정규화하고 같은 입력은 한 번만 임베딩해요. 예를 들어 `esim이 뭐야?`와 ` esim이  뭐야？？？ `는 같은 키로 등록돼요. DB의 유니크 제약으로 요청 간 중복도 막아요. 원래 표현은 표시용 `question`에 유지하고, 실제 임베딩 입력은 `normalizedQuestion`으로 확인해요.

대소문자·동의어·어미는 통합하지 않아요. `?`와 `!`도 서로 다른 기호로 유지해요. 줄바꿈·문장 경계·부정·조건·추가 요청은 지우지 않아요. `esim이 뭐야?? 어디서 발급받아??`는 두 물음표 구간이 남아 캐시에서 제외돼요. 정규화 후 비어 있는 표현은 `FAQ-012`로 거절해요.

임베딩은 기존 `EmbeddingService`를 사용하고 기본 8개씩 나눠 호출해요. `FAQ_CACHE_REGISTRATION_BATCH_SIZE`로 1~50 범위에서 조절할 수 있어요. 모델 호출 중에는 FAQ 잠금이나 DB 트랜잭션을 유지하지 않아요. 호출이 끝난 뒤 FAQ를 잠그고 승인·공식 내용·버전·벡터를 재확인해요. 바뀌었다면 `FAQ-009`로 전체 등록을 거절해요. 등록 중 하나라도 DB 저장에 실패하면 전체를 롤백해요.

POST는 입력한 표현만 추가·갱신하며 기존 표현을 자동 제거하지 않아요. 제거할 때는 DELETE를 명시적으로 호출해요. DELETE는 해당 표현의 벡터를 검색에서 제외하는 동작이에요. 같은 사용자 질문이 다른 유효 표현과 매칭될 수는 있어요. FAQ 전체의 직접 답변을 막으려면 `cacheable=false`로 바꿔요. 비활성화된 표현을 같은 프로필로 다시 POST하면 임베딩·최신 FAQ 검증 후 재활성화해요. 같은 FAQ·프로필·문자열을 반복 등록해도 중복 행을 만들지 않아요.

GET에는 `id`, `faqId`, `profileId`, `question`, `enabled`, `valid`, `faqVersion`, `currentFaqVersion`, `createdAt`, `normalizedQuestion`, `normalizationVersion`을 반환해요. `valid`는 현재 정규화 버전·프로필·FAQ 승인·본문·버전·질문 벡터와 일치하는지 나타내요. 사용자 질문의 유사도 판정까지 통과했다는 뜻은 아니에요. 다른 프로필과 오래된 표현도 조회되지만 `valid=false`로 표시해요.

FAQ 내용·버전이 바뀌면 GET으로 검토할 표현을 확인하고 해당 표현을 다시 POST한다. 새 FAQ도 승인과 유효한 표현 등록을 마치면 코드나 리소스의 ID 목록을 수정하지 않고 검색·판정 대상이 된다. 등록 완료가 HIT를 보장하지는 않으며 공통 유사도·경쟁 점수 차이·최신 FAQ 검증을 통과해야 한다.

이전 `scripts/semantic-cache/` 도구와 `catalog-reviewed.json`은 과거 실험의 참고 자료예요. 현재 정규화 등록은 Java API로 진행해요. 이전 도구로 넣은 벡터는 정규화 버전 0이므로 현재 캐시 검색에 사용되지 않아요. 카탈로그에 있는 표현은 검토 후 Java API로 등록해요.

## 6. 확인 방법

전체 테스트·빌드:

```text
gradlew.bat test build --no-daemon
```

전체 테스트의 DB는 Testcontainers가 새로 만들어요. 실제 모델 서버를 사용하는 선택 테스트는 해당 서버를 준비했을 때 따로 실행해요. 자동 테스트 통과가 실제 모델 응답 품질을 보장하지는 않아요.

실제 API는 `POST /chat/questions`에 다음 JSON을 보내요. 서버 포트는 실행한 서버의 포트로 맞춰요.

```json
{"question":"esim이 뭐야?"}
```

응답 JSON에는 캐시 여부 필드가 없으므로 서버의 해당 `attemptId` 로그를 확인해요.

- `source=FAQ_OFFICIAL`: 공식 답변 반환, LLM 생략.
- `source=LLM`: 기존 LLM 경로 선택. 호출 성공 여부는 최종 응답도 확인해요.
- `source=INSUFFICIENT_FAQ`: 기존 검색 근거 부족.

전체 응답 시간은 HTTP 클라이언트에서 측정해요. `preparationMs`는 LLM 생성 전까지의 시간이에요. 모델 첫 로딩은 별도로 기록하고, 같은 DB·모델·질문으로 캐시 ON/OFF를 비교해요.

정상 표현뿐 아니라 발급 방법·개인 조회·복합 질문·새 번호 요청·번호이동을 하지 않는 조건도 확인해요. 승인 해제나 FAQ 삭제 후 이전 검색 결과로 공식 답변을 반환하면 안 돼요. 승인 해제·재승인으로 버전이 바뀌면 표현을 다시 등록해요.

## 7. 한계

등록 표현·코사인 유사도·경쟁 점수 차이와 공통 제외 규칙은 모든 동의 표현·부정·문맥을 판별하지 못한다. 기존 실험에서는 새 번호 요청·번호이동 부정·문맥 의존 질문을 통과시킨 사례가 있었다. 5개 FAQ 전용 주제·조건·어휘 규칙은 현재 흐름에서 제거했으므로, 과거 정책의 차단 결과도 현재 구성의 보장으로 사용하지 않는다. 승인 범위를 늘릴 때는 공식 답변으로 전체 질문을 해결할 수 있는지 검토하고 등록하지 않은 정상·다른 의도·복합·개인 조회 질문으로 다시 검증해야 한다.

동적 임계값, 질문 정확 일치부터 단계별로 처리하는 계층적 캐시, 캐시 전용 운영 메트릭·비용 계산은 추가하지 않았어요. 일반 Actuator/Prometheus 지표와 판정 로그는 사용할 수 있어요. 운영 활성화 전에는 실제 사용 질문과 팀 검토로 허용 범위를 확인해야 해요.
