# 관리자 분석 모델의 작업별 실행

관련 이슈: #278. 이 문서는 배치 준비용이며 실제 EC2에 적용된 설정을 뜻하지 않습니다.

관리자가 분석을 실행하거나 기존 예약 주기가 도래하면 `ReviewWorker`가 중앙 제어기에 사용권을 요청합니다.
준비 완료 후 기존 분석 프롬프트로 후보·출처·위험 유형·의심 사유를 수집하고, 마지막 사용권을 반납하면
관리자 모델 컨테이너만 정지합니다. 모델 파일은 디스크에 보존합니다.
후보 승인·오차단 재검사·경고 중복 묶기·알림은 기존 관리자 기능을 재사용합니다.

## 코드 연결

1. 기존 DB 작업 사용권을 유지하며 `PUT /leases/<UUID>`로 전용 모델을 준비합니다.
2. 분석 묶음에는 모델 사용권 하나를 사용하고 각 항목의 진행률을 저장합니다.
3. 전용 모델도 기존 `LlmService`의 채팅 우선 입장 제어를 따릅니다. 여유가 없으면 항목을 완료로 처리하지 않고 양보합니다.
4. 새 오차단 검사가 대기 중이면 현재 항목 후 모델과 작업 사용권을 반납합니다.
5. 정상 완료·분석 실패·장애 재시도 시 사용권을 반납합니다. 기존 연결 장애·시간초과 재시도와 출력 거절 재시도 금지 정책은 유지합니다.

`ReviewModelClient`는 기존 OpenAI 호환 클라이언트의 직렬화·추론 텍스트 제거·오류 처리를 재사용합니다.
전용 주소가 없거나 다른 모델이 응답하면 공통 모델로 대체하지 않습니다.
모델 설정을 추가하는 것만으로 기존 예약 작업의 활성화 여부나 주기를 변경하지는 않습니다.

## EC2 담당자 준비 사항

- 공식 `Qwen/Qwen3-14B-AWQ`, revision `31c69efc29464b6bb0aee1398b5a7b50a99340c3`의 완전한 체크포인트를 별도 경로에 준비합니다. `quant_method=awq`, `bits=4`를 확인합니다.
- 이미 검증한 vLLM 이미지 ID 또는 고정 digest를 선택합니다. 제어기는 다운로드나 이미지 pull을 하지 않습니다.
- [compose 예시](../../infra/guard-review-runtime/compose.example.yaml)를 기존 서비스와 별도 프로젝트에서 검토합니다. `GUARD_REVIEW_RUNTIME_IMAGE`, `GUARD_REVIEW_AWQ_CHECKPOINT`가 필요합니다.
- `create`로 `ubot-admin-risk-qwen14` 컨테이너만 준비합니다. `up`으로 상시 로드하지 않습니다. `restart: no`를 유지합니다.
- 모델 이름과 `ubot.guard-review-runtime=qwen3-14b-awq` 라벨이 모두 일치해야 제어기가 시작·정지를 허용합니다. 확인한 컨테이너 ID로만 조작합니다.
- EC2 Linux 호스트에서 Python 표준 라이브러리 기반 `controller.py`를 실행할 계정과 복구 방식을 준비합니다. Docker 제어 권한은 서버 관리 권한에 준합니다. 백엔드에 Docker 소켓을 연결하지 않습니다.
- `GUARD_REVIEW_RUNTIME_TOKEN`에 32자 이상의 비밀값을 별도 주입합니다. 실제 값은 Git·PR·로그에 남기지 않습니다.
- 제어 프로그램은 상주하지만 모델은 유휴 시 로드하지 않습니다. 같은 컨테이너를 제어하는 프로그램은 하나만 실행합니다.

검토 후 별도 생성하는 명령 예시(이 코드가 자동으로 실행하지 않음):

```sh
docker compose --project-name ubot-admin-risk -f compose.example.yaml --env-file compose.env create --no-recreate admin-risk-qwen14
python3 controller.py
```

제어기 기본 연결은 `127.0.0.1:18176`, 전용 모델은 `127.0.0.1:18175`입니다.
컨테이너 안의 Worker에서 `127.0.0.1`은 EC2 호스트가 아닙니다. EC2 담당자와 Worker의 실제 실행 위치를 확인하고
접근 제한된 사설 프록시 등 연결 경로를 확정해야 합니다. 예시 포트를 인터넷에 공개해서 해결하지 않습니다.
현재 제어기의 바인딩 주소·포트는 고정입니다. 다른 통신 구성이 필요하면 배치 전에 별도 보완이 필요합니다.

Worker에 전달할 전용 환경변수는 [설정 참조](../reference/configuration.md#관리자-위험-표현-분석-전용-모델-설정)를 따릅니다.
기존 배포 Compose에 변수 전달까지 자동 추가하지 않았으므로 EC2 담당자가 Worker 환경에 주입해야 합니다.

## 자원과 장애 동작

- 시작 기준: GPU 0의 여유 VRAM 21,500MiB 이상, 호스트 `MemAvailable` 10,000MiB 이상.
- `GUARD_REVIEW_MIN_GPU_MIB`로 초기 GPU 기준을 조정할 수 있으나 실측 없이 낮추면 정상 로딩이 보장되지 않습니다.
- 예시: GPU 메모리 사용률 0.88, 문맥 길이 32,768, 동시 시퀀스 2, 컨테이너 RAM 9GiB.
- 자원이 부족하면 `503 GPU_BUSY`로 응답합니다. 다른 모델이나 사용자 서비스를 내리지 않습니다. 자원을 확보하지 못하면 분석은 계속 대기할 수 있습니다.
- 모델 준비 제한 240초, 백엔드 제어 요청 기본 제한 300초. 실제 GPU와 이미지에서 확인해야 합니다.
- 사용권 갱신은 30초마다 진행하며 마지막 갱신 후 900초에 만료합니다. 제어기는 10초마다 만료를 확인합니다.
- 다른 Worker의 유효한 사용권이 있으면 모델을 유지합니다. 마지막 사용권이 없어지면 전용 컨테이너를 정지합니다.
- Worker 강제 종료나 반납 통신 실패 시 즉시 해제를 보장하지 않습니다. 제어기가 살아 있으면 만료 정리가 동작합니다.
- 제어기가 강제 종료되면 다음 기동 시 자기 소유 모델의 잔여 컨테이너만 정리합니다. 따라서 제어기 복구가 필요하고 분석 중 재시작은 피해야 합니다.

## 검증 범위

Java 연결 테스트는 가짜 HTTP 응답과 모델 호출을, Python 테스트는 가짜 Docker 실행기를 사용합니다.
실제 모델 판정 성능, EC2 VRAM 해제량, Docker 이미지 호환성, 장시간 동시 사용, 배포 네트워크와 PostgreSQL 연동은
이 단위 검증만으로 확인되지 않습니다. 실제 배포 전에 별도 확인해야 합니다.
