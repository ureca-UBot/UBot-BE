# AI 금칙어·위험 문장 검토

가드 전 LLM 응답과 출처별 검사 기록에서 관리자 검토 후보를 찾습니다. FAQ 사실성 검사는 수행하지 않습니다.
후보는 승인 전까지 금칙어에 반영되지 않으며, 위험 문장은 관리자 경고로만 사용합니다.

## 관리자 흐름

1. `/admin/guard-review/settings`에서 사용 여부·주기·경고 묶기 임계값을 저장합니다.
2. API 역할의 스케줄러가 새 차단 검사 기록을 분석 대기열에 넣습니다. 수동 `/analysis`는 보관 중인 동일 대상의 전체 재분석이며, 보류 기록의 선택 재검토와 구분합니다.
3. Worker가 원문 스냅샷을 기존 LLM 창구로 분석합니다. 모델 응답은 원문 포함 여부·유형·크기를 다시 검사합니다.
4. 금칙어 후보는 수정 후 `/validation`으로 오차단 검사를 실행합니다. 정상 정보 손실이나 기존 차단 회귀가 있으면 승인할 수 없습니다.
5. `/approval`은 검사한 후보 묶음·버전·기존 금칙어·검사 코드·검증 자료가 같은 경우에만 기존 금칙어 서비스를 통해 적용합니다.
6. 위험 문장은 기존 알림 시스템으로 관리자에게 전달합니다. 동일 원문 버전은 반복 통보하지 않고, 새로운 사례가 발견되면 다시 알립니다.

관리자는 검증된 후보를 승인하거나 적용을 해제할 수 있습니다. 경고 확인·읽음 처리는 차단 등록이 아닙니다.
수동 금칙어 변경과 승인은 같은 잠금을 사용하고, 분리된 프로세스의 캐시도 주기적으로 갱신합니다.

## 마이그레이션과 데이터

기존 V48·V49는 변경하지 않습니다. 이번 확장은 V53(가드 전 응답 수집), V54(가드 결과 구분), V55(검사 출처 기록), V56(보류 재검토 결과)을 순서대로 적용합니다.
마지막 마이그레이션 번호는 PR 병합 전에 다시 확인해야 합니다. 이미 병합된 마이그레이션은 수정하지 않습니다.

새 테이블은 다음 여섯 개입니다.

| 테이블 | 역할 |
|---|---|
| `guard_review_settings` | 분석 사용 여부·주기·임계값·설정 버전 |
| `guard_review_runs` | 분석·검사 실행 및 Worker 소유권 |
| `guard_review_items` | 원본 연결·질문/답변 스냅샷·성공 내용 지문 |
| `guard_review_candidates` | 금칙어 후보 및 경고 묶음 |
| `guard_review_findings` | 원본 버전별 발견 사례·알림 중복 방지 |
| `guard_review_history` | 관리자 수정·승인·해제 기록 |

기본 설정 한 행만 생성하며 자동 분석은 꺼져 있습니다. 가짜 후보·경고·사용자를 운영 DB에 넣지 않습니다.
기존 알림에는 `GUARD_REVIEW` 유형과 후보 연결 컬럼을 추가합니다. 실제 DB 적용은 배포 시 Flyway가 수행합니다.
DB 변경은 팀 규칙에 따라 DB 담당 리뷰가 필요합니다.

상세 자료는 30일, 실행 요약은 90일, 변경 이력은 365일 기준으로 정리합니다.
마지막 성공 지문·후보·발견 연결·알림 중복 정보와 마지막 변경 이력은 보존합니다.
보관기간이 지난 검사로는 승인할 수 없고 다시 검사해야 합니다.

## 가짜 응답 테스트

```powershell
.\gradlew.bat test --tests 'com.ubot.guardreview.*'
```

프로젝트의 `PgvectorTestConfiguration`을 재사용하여 Testcontainers 전용 PostgreSQL을 만듭니다.
개발 DB 설정이나 개인 파일 경로는 필요하지 않습니다. 실제 LLM·임베딩은 호출하지 않습니다.
가짜 모델·질문·답변·사용자와 실패 주입은 테스트 코드에만 존재합니다.

금칙어 후보 검사의 기준 사례는 `src/main/resources/guard-review/golden-cases.json`에 들어 있습니다.
기존 시험용 금칙어 목록은 테스트 리소스에만 있으며 운영 금칙어를 덮어쓰지 않습니다.
기준 검사는 입력 공통 검사와 금칙어 단계의 전후 비교이며, 출력 가드의 FAQ 사실성 전체 평가를 대신하지 않습니다.

실제 모델의 후보 판정 품질·임베딩 유사도 임계값, 운영 JWT·배포 구성·예약 실행 시각은 별도 검증이 필요합니다.


## 운영에서 사용하는 오차단 검사 자료

금칙어 후보 검사의 기준 사례는 `src/main/resources/guard-review/golden-cases.json`에 있습니다. 테스트에서도 재사용하지만 관리자 기능이 운영 중 직접 읽는 기준 자료이므로 JAR에 포함합니다.

- 검사 접수 시 API의 `ReviewService.startValidation()`이 자료의 해시(`datasetVersion`)와 전체 사례 수를 읽어 검사 요청에 기록합니다.
- `ReviewWorker`는 접수된 자료 버전과 현재 버전이 같은지 확인한 뒤, `ReviewValidationService.dataset()`으로 사례를 읽어 기존 금칙어 목록과 후보 추가 목록의 결과를 비교합니다. 실제 LLM·Judge는 호출하지 않습니다.
- 승인 시에도 현재 자료 해시를 접수·결과 버전과 비교합니다. 자료가 바뀌면 기존 통과 결과를 그대로 승인하지 않고 다시 검사해야 합니다.
- 자료는 `ClassPathResource`로 읽습니다. `src/test/resources`로 옮기거나 배포에서 제외하면 운영 중 검사 접수·실행·승인에 필요한 자료를 읽을 수 없습니다. 별도 외부 경로나 서버 설정은 추가하지 않습니다.
- 이 파일을 배포해도 질문·답변·금칙어를 DB에 삽입하거나 금칙어를 자동 적용하지 않습니다. 기준 검사는 입력 공통 검사와 금칙어 단계의 전후 비교이며, 출력 가드의 FAQ 사실성 전체 평가나 모든 새 문맥의 안전성을 보장하지 않습니다.

실제 모델의 후보 판정 품질·임베딩 유사도 임계값, 운영 JWT·배포 구성·예약 실행 시각은 별도 검증이 필요합니다.

## 사용자 채팅과 분석 호출 우선순위

- 관리자 분석은 기존 `LlmService`와 같은 전체 동시 호출 상한을 사용하면서, 분석 호출 자체도 인스턴스당 최대 1건으로 제한합니다. 서버 설정을 추가하거나 전체 상한을 늘리지 않습니다.
- 전체 상한이 2 이상이면 빈 슬롯이 2개 이상일 때만 분석을 시작하고, 실제 호출에는 1개만 사용합니다. 기본 상한 4에서는 채팅이 3개 슬롯을 쓰는 동안 분석을 미루며, 분석 실행 중에는 채팅이 나머지 3개 슬롯을 사용할 수 있습니다. 대기 중인 사용자 호출을 앞지르지 않도록 공정한 즉시 획득을 사용합니다.
- 여유 부족은 기다리거나 모델을 호출하지 않고 다음 Worker 주기로 미룹니다. 항목은 `PENDING`으로 두고 lease만 반납하며, 실패·성공 지문·완료 건수로 확정하지 않습니다. 실제 모델 오류의 기존 실패 처리는 유지합니다.
- 사용자 답변과 질문 정리용 `generateJudgment`는 기존 경로를 유지합니다. 진행 상태·질문별 취소·출력 가드 거절 시 재시도 금지 정책은 변경하지 않습니다.
- 전체 상한이 1이면 유휴 상태에서만 분석을 시작합니다. 실행을 시작한 모델 호출을 새 채팅 때문에 강제 중단하지는 않습니다. 이 제한은 기존 세마포어와 같이 프로세스 내 `LlmService` 인스턴스 기준이며, 여러 Worker 프로세스에 대한 서버 전체 제한은 아닙니다.

## 스냅샷 생성과 작업 완료 잠금

- 수동·예약 분석 접수와 실패 분석 재개는 분석 등록 전용 advisory lock으로 직렬화합니다. 스냅샷 삽입 중에는 후보·발견 기록 완료, 알림 전송, 보관기간 정리가 사용하는 잠금을 잡지 않습니다.
- 분석 실행 등록·원문 동결·전체 건수 확정은 하나의 트랜잭션으로 유지합니다. 커밋 전에는 Worker가 미완성 실행을 가져갈 수 없고, 실패하면 부분 스냅샷과 실행도 함께 롤백됩니다.
- 스냅샷은 여전히 동기 SQL 한 문장입니다. 대규모 자료의 생성 시간·DB 부하는 운영 규모에서 별도 측정해야 하며, 이번 변경은 완료·알림과 공유하던 잠금을 분리하는 범위입니다.

## 분석 장애와 긴 검증 실행

- 분석 실행 자체의 실패는 검증 완료 함수와 분리합니다. 실제 완료·실패 항목 수로 `processed`를 계산하고, `result`에 `completed`·`failed`·`pending`과 오류 코드를 남깁니다. 미처리 항목을 완료로 바꾸지 않습니다. 검증도 실패 시 전체 건수를 처리한 것으로 덮어쓰지 않습니다.
- 분석의 LLM 연결 실패(`LLM-003`)와 시간 초과(`LLM-004`)만 같은 항목을 10초·30초 후 재시도합니다. 대기 시각과 연속 실패 수는 기존 실행 행에 저장하므로 다른 Worker와 재시작 후에도 적용됩니다. 세 번째 실패면 해당 항목 하나만 실패로 확정하고 실행을 멈춥니다. 나머지 항목은 대기 상태로 보존하고 관리자가 재개할 수 있습니다. 정상 처리·수동 재개 시 연속 실패 기록을 초기화합니다.
- 잘못된 분석 JSON·원문에 없는 후보 등은 기존 항목 실패 정책을 유지합니다. 사용자 채팅의 자동 재시도·출력 가드 거절 시 재시도 금지는 변경하지 않습니다. 호출 슬롯 부족으로 다음 주기로 미루는 경우도 장애 횟수에 넣지 않습니다. 분석이 대기하는 동안 검증은 계속 우선 접수할 수 있습니다.
- 관리자 검토 Worker에만 전용 daemon 타이머를 두고 30초마다 기존 5분 lease를 갱신합니다. 실행 ID·토큰·미만료·실행 중 상태가 모두 같은 경우에만 연장합니다. 종료된 작업·오래된 소유자는 되살리지 않습니다. 완료 후 해당 갱신 예약을 해제하고, 컨텍스트 종료 시 자기 타이머만 종료합니다.
- 갱신 실패·소유권 상실은 검증 사례 사이에서 확인해 계산을 중단하고 결과·실패를 덮어쓰지 않습니다. 이미 시작된 모델 요청을 이 타이머가 원격에서 취소하지는 않으며, 요청이 돌아오면 소유권을 확인한 뒤 저장을 생략합니다. DB 장애나 긴 프로세스 정지 후에는 lease 만료 복구 특성상 계산이 일부 중복될 가능성이 남습니다.
- 5,168건 전체 자료의 단일·최대 50개 후보 검증 시간을 가짜 데이터로 측정합니다. 이는 로컬 측정이며 운영 장비·실제 금칙어 수·동시 부하에서의 상한을 보장하지 않습니다.

## 실행 조회 응답과 검사 사례 페이지

- 개요의 실행 목록과 `GET /admin/guard-review/runs/{id}`는 동일한 요약 응답을 사용합니다. `result`는 JSON 문자열이 아닌 객체이고 `cases` 본문은 포함하지 않습니다. 검증 결과에는 현재 보관 중인 `caseCount`를 함께 제공합니다. 실행 건수·성공 기준·오차단/회귀 집계·버전 등 나머지 요약은 유지합니다.
- DB 조회 단계에서 `result-'cases'`로 본문을 제외하며, Worker의 종류·상태 확인도 이 요약 경로를 사용합니다. 전체 동결 요청·lease 내부 값은 실행 조회에 읽어 오지 않습니다.
- 검사 사례는 `GET /admin/guard-review/runs/{id}/cases?page=0&size=20`으로 조회합니다. 페이지는 0부터 시작하고 크기는 10·20·50만 허용합니다. 기존 `PageResponseDto`의 `content`·`page`·`size`·`totalElements`·`totalPages`·`first`·`last`를 재사용하며, 배열에 저장된 순서대로 제공합니다. 페이지 범위를 벗어나면 빈 `content`를 반환합니다.
- 관리자만 완료된 VALIDATION 실행의 보관 중인 사례를 조회할 수 있습니다. 없는 실행은 404, ANALYSIS 실행·잘못된 페이지 값은 400, 미완료·만료된 검증 상세는 409입니다. 원문 상세가 만료되면 물리 정리 전이라도 사례를 반환하지 않습니다. 상태·건수·페이지를 같은 읽기 스냅샷으로 조회합니다.
- 사례 페이지는 DB에서 요청한 배열 인덱스만 꺼내 Java로 전달합니다. 클라이언트나 Java 서비스에서 전체 5,168개 사례를 읽은 뒤 잘라내지 않습니다. 기존 JSONB 저장 구조와 보관기간 정리 정책은 변경하지 않습니다.
- 승인 시에는 내부 전용 전체 결과 조회로 기존 버전·후보 묶음·검사 통과 여부 검사를 그대로 수행합니다. 요약 응답이나 클라이언트가 보낸 통과 여부만으로 승인하지 않습니다.
- 프론트 후속 연동: 현재 `ReviewRun.result: string`·`JSON.parse`와 전체 `cases`를 기대하는 파서/승인 버튼 조건은 새 객체 요약·`caseCount` 및 사례 페이지 API에 맞춰 수정해야 합니다. 이번 백엔드 보완에서는 프론트를 수정하지 않습니다. 연동 전 배포하면 기존 결과 표시·승인 버튼이 동작하지 않을 수 있으므로 함께 반영해야 합니다.

## 명시적 검사 규칙 버전

- `ReviewValidationService.RULES_VERSION`에 규칙 계약 버전을 둡니다. 현재 값은 `guard-review-rules-v2`입니다. v2에는 AI 후보의 최소 적용 길이 기준이 포함됩니다. `.class` 바이트·컴파일러·빌드 시각·배포 번호는 참조하지 않습니다.
- `baseVersion`은 규칙 버전과 정렬한 활성 금칙어 목록을 JSON 배열로 인코딩한 SHA-256입니다. 금칙어 순서는 영향을 주지 않고, 줄바꿈 등을 포함한 한 표현과 여러 표현도 구분합니다. 기존 `datasetVersion`은 검사 자료 해시로 분리한 채 유지합니다.
- 규칙 버전·활성 금칙어·검사 자료가 같으면 API와 Worker의 빌드가 달라도 재검사를 요구하지 않습니다. 실제 검사 동작이 달라지면 상수를 올리고 API와 Worker를 같은 버전으로 맞춘 후 재검사합니다. 롤링 중 규칙 버전이 다른 요청은 Worker가 계산 전에 거절하고, 승인에서도 기존 요청·결과·현재 버전 비교를 유지합니다.
- 버전을 올릴 대상은 정규화·금칙어 매칭·입력 가드와 프롬프트 조작 검사·출력 금칙어 단계·정상 내용 보존/회귀 비교·차단 결과 해석 등 이번 검사의 결과를 바꾸는 변경입니다. 무관한 화면·로그·lease·동작이 같은 리팩토링·재빌드만으로는 올리지 않습니다. 앞으로 규칙 변경 PR에서 이 상수 갱신을 확인해야 합니다. 갱신을 빠뜨린 의미 변경을 자동 탐지하는 장치는 추가하지 않았습니다.
- 클래스 해시 방식에서 이 방식으로 처음 전환할 때는 이전 `baseVersion`으로 만든 대기 요청·검사 결과를 승인하지 않습니다. 저장된 버전을 고쳐 쓰거나 기존 버전 비교를 우회하지 않고, 두 프로세스 갱신 후 다시 검사합니다. DB 마이그레이션이나 설정 추가는 필요하지 않습니다.

## 짧은 AI 금칙어 후보의 적용 제한

- 기존 금칙어 서비스·캐시·입력/출력 가드·이미 등록된 금칙어는 변경하지 않습니다. 이 제한은 새 관리자 AI 후보 경로에만 적용합니다. 기존 수동 등록 경로의 정책이나 이미 적용된 짧은 금칙어를 자동 변경하지 않습니다.
- AI WORD 후보는 정규화 후 문자·숫자가 3자 이상이어야 수정 저장·검사·승인할 수 있습니다. 기존 `SafetyTextNormalizer`의 NFKC 처리를 재사용하고 공백·서식 문자·문장부호·UTF-16 surrogate 길이로 길이를 부풀리지 않습니다. 공백 등으로 분리된 자모는 합친 뒤 셉니다.
- 모델이 1~2자 또는 유효 문자가 부족한 WORD를 제안하면 기존 WARNING 경로로 보존합니다. 원문 포함 여부·유형·의도 검사는 그대로 수행하고, 기존 경고 묶기·발견 사례·알림을 재사용합니다. 함께 찾은 다른 정상 후보를 버리거나 원문을 수정하지 않습니다. 경고가 곧 위험성 확정이나 금칙어 등록을 뜻하지는 않습니다.
- 관리자가 짧은 표현으로 수정하거나, 예전에 저장된 짧은 후보·비활성 금칙어 연결로 검사/승인을 시도하면 `GUARD-REVIEW-008`(400)로 거절합니다. 더 구체적인 표현으로 수정하거나 반려할 수 있습니다. 이미 활성화된 금칙어의 적용 해제는 계속 가능합니다. 실제 DB의 기존 후보나 금칙어를 일괄 변환하지 않습니다.
- 3자 기준은 보수적인 최소 적용 자격이며 위험도 점수나 안전성 보장이 아닙니다. 3자 이상인 일반 표현도 정상 문의를 막을 수 있고, 골든 자료에 없는 문맥의 오차단은 놓칠 수 있습니다. 기존 골든 오차단/회귀 검사와 관리자 원문·발견 이유 검토를 계속 거친 후 승인합니다. 특정 표현 허용 목록이나 추가 LLM/Judge 판정은 만들지 않습니다.
- 검사 후보의 자격 판정이 바뀌므로 규칙 계약을 `guard-review-rules-v2`로 올렸습니다. v1로 검사한 결과를 그대로 승인하지 않고 API·Worker를 같은 버전으로 맞춘 후 재검사합니다.

## 중복키의 식별자 보존 제한

- 분석 스냅샷의 `source_key`는 기존 대화·사용자·멱등키 조합을 SHA-256으로 변환해 저장합니다. 관리자 API에서도 `sha256:` 형식의 가명 키만 반환합니다.
- V49는 기존 항목·발견 기록의 키에도 같은 변환을 적용하며, 지문·연결·알림 상태를 유지합니다. 원문 전체의 익명화를 의미하지 않으며 상세 스냅샷의 기존 30일 보관·정리 기준은 유지합니다.
- 가드 전 응답 수집과 검사 기록은 별도 트랜잭션으로 남기며, 저장 실패가 기존 가드 판정을 변경하지 않게 합니다.
- 최초 기능 마이그레이션은 아직 미병합이므로 V48로 이동하고, 기존 키 변환을 V49로 추가합니다. 팀원 마이그레이션은 변경하지 않습니다.


## 가드 검사 기록과 원본 응답

- LLM 최종 응답은 파싱·출력 가드 전에 질문 원문과 연결해 `guard_review_items`에 수집합니다. 실제 생성 응답만 수집하며 공식 FAQ 캐시를 LLM 원문으로 간주하지 않습니다.
- `guard_review_checks`는 INPUT_CODE, INPUT_LLM, OUTPUT_CODE, OUTPUT_LLM을 구분합니다. PASS, FILTERED, REJECTED, REVIEW, ERROR, SKIPPED, UNKNOWN은 서로 다른 결과이며 미실행을 통과로 집계하지 않습니다.
- 접수 전에 거절된 입력은 시도 ID와 답변 없이도 기록합니다. 출력 검사에는 당시 질문·답변·FAQ·대화·추가 자료·조회 근거를 보존합니다. 현재 FAQ로 과거 근거를 재구성하지 않습니다.
- 목록은 `GET /admin/guard-review/checks`, 상세는 `/checks/{id}`입니다. 기존 관리자 권한을 적용합니다. 후보·발견 사례의 출처와 판정 필터는 AND로 적용하고 발견 횟수도 같은 조건으로 계산합니다.
- 새 검사 이력의 자동·전체 분석은 실제 REJECTED만 사용합니다. 이전 수집 기록은 새 출력 검사 이력이 없는 시도만 기존 경로로 처리해 중복 분석을 피합니다.
- 입력 분석은 사용자 질문의 위험 표현을 찾습니다. 출력의 사실 오류 의심은 당시 근거를 대조해 WARNING/FACTUAL_ERROR로만 제안하며 WORD로 적용하지 않습니다. 모델 의견은 확정된 오류 판정이 아닙니다.
- 원문 상세는 30일, 검사 요약은 90일 보관합니다. 저장 장애는 본문 없이 경고하며 기존 사용자 응답과 가드 오류를 유지합니다. 기록 트랜잭션 제한은 2초이고 실제 부하는 별도 측정해야 합니다.

## 관리자가 선택한 보류 기록 재검토

- `POST /admin/guard-review/reassessment`에 origin과 checkIds를 보냅니다. INPUT_LLM 또는 OUTPUT_LLM의 REVIEW 기록만 페이지당 최대 50건 선택합니다.
- 서버는 출처·판정·ID·상세 보관기간을 모두 검증하고 선택 자료를 동결합니다. 한 건이라도 만료되거나 조건이 다르면 전체 접수를 거절합니다.
- 기존 관리자 14B Worker·호출 우선순위·모델 실행/해제·lease와 장애 재시도를 재사용합니다. 사용자 채팅 경로에 추가 분석 호출을 넣지 않습니다.
- 정상 가능성, 문제 의심, 자료 부족·판단 불가 의견을 저장합니다. 문제 의심일 때만 기존 단어 후보·문장 경고에 연결합니다. 원래 REVIEW 판정·사용자 답변·운영 금칙어를 자동 변경하지 않습니다.
- 재검토는 원래 검사 기록을 덮어쓰지 않고 실행별 결과를 `guard_review_items.reassessment`에 저장합니다. 상세 보관기간이 만료되면 함께 정리합니다.
- 단위·연결 테스트는 가짜 모델을 사용합니다. 실제 DB 적용·EC2 모델 품질·부하는 별도 검증 대상입니다.


## 예약 분석 출처와 리뷰 보완

- 기본 `analysisSource`는 `GENERATED_ANSWER`입니다. 출력 가드 전 생성 답변을 모두 분석하며, 후속 가드의 PASS/FILTERED/REJECTED/REVIEW/ERROR/SKIPPED로 분석 대상을 좁히지 않습니다. 아직 처리 중인 PENDING 원본은 결과가 정해진 뒤 가져옵니다. 공식 FAQ 캐시처럼 LLM 응답 자체가 없는 경로에는 가짜 생성 답변을 만들지 않습니다.
- `INPUT_LLM`, `OUTPUT_LLM`, `INPUT_CODE`, `OUTPUT_CODE`를 설정하면 해당 출처의 실제 PASS/FILTERED/REJECTED 기록만 분석합니다. REVIEW는 기존 선택 재검토 API를 유지하고, ERROR/SKIPPED를 정상 판정이나 차단 판정으로 분석하지 않습니다.
- 1주일은 `intervalMinutes: 10080`입니다. 예약 시각마다 저장된 출처와 모드를 실행 요청에 고정하고 원문을 동결합니다. 설정을 바꿔도 진행 중인 실행의 자료는 바뀌지 않으며 다음 실행부터 새 출처를 사용합니다.
- 주기 실행은 INCREMENTAL입니다. 같은 원본 키의 최신 성공 지문이 같으면 제외하며, 신규·변경 원본과 성공 이력이 없는 실패 원본은 다시 선택합니다. 출처별 원본 키가 달라 옵션을 전환해도 다른 출처의 성공 이력 때문에 누락되지 않습니다. 수동 FULL은 선택한 출처를 다시 분석합니다.
- 서로 다른 질문/생성 시도는 내용이 같아도 각각의 원본입니다. 반복 주기에서 같은 원본을 중복 분석하지 않는 것과, 별개 기록을 하나로 합치는 것은 다릅니다.
- 상세 원문은 기존 30일 보관 범위에서만 분석할 수 있습니다. 최신 성공 지문은 기존 정리 정책대로 보존하며, 만료된 원문을 AI가 다시 읽을 수 있는 것처럼 표시하지 않습니다.

설정 예시 (`PATCH /admin/guard-review/settings`, 관리자 인증 필요):

```json
{
  "enabled": true,
  "intervalMinutes": 10080,
  "groupingThreshold": 0.95,
  "revision": 1,
  "analysisSource": "INPUT_LLM"
}
```

기존 클라이언트가 `analysisSource`를 생략하면 저장된 출처를 유지합니다. 신규 설정의 기본은 `GENERATED_ANSWER`입니다. 프론트 설정 드롭다운은 이번 백엔드 작업에 포함하지 않았습니다.

### 검사 기록과 저장 비용

- FILTERED는 본문 문자열 차이가 아니라 `contentRemoved`/`SlotOutcome.changedByGuard`로 기록합니다. ABSTAIN 칸 제외, 고지문 추가, 코드의 상품 목록 생성으로 본문이 달라져도 가드가 제거한 것이 아니면 PASS입니다.
- HTTP 질문 접수에서 정상 PASS/검사 OFF를 중복 INSERT하지 않습니다. 접수 단계의 차단·오류, 실제 LLM 검사 PASS, 가드 전 생성 답변 수집은 유지합니다.
- 요청마다 최대 3개씩 만들던 NOT_CALLED 기록은 `origin=UNKNOWN`, `outcome=SKIPPED`, `skippedOrigins` 배열을 가진 한 요약으로 저장합니다. 출처 필터는 이 배열도 조회하며 과거의 개별 SKIPPED 행도 읽을 수 있습니다. 실제 실행했으나 기록 저장에 실패한 검사를 SKIPPED로 바꾸지 않습니다.
- SKIPPED에는 FAQ·대화·카드를 저장하지 않습니다. 실제 검사 및 생성 원본은 이후 위험 표현/근거 검토를 위해 필요한 질문·답변·FAQ 근거·추가 근거·대화를 보관합니다. FAQ 검색 점수/중복 variant, 시스템 프롬프트, 금칙어 사전, 원문 답변의 문맥 내 복제와 화면용 tool_records 카드는 제외합니다. 조회 operation과 비교에 필요한 텍스트 근거는 유지합니다.
- V56에 보류 재검토 결과와 분석 출처 설정, 검사 생략 요약 컬럼·조회 인덱스를 함께 추가합니다. 별도의 V58 파일이나 새로운 테이블은 없습니다. 기존 V56/V58을 적용한 환경은 배포 전에 DB 담당자가 적용 이력과 체크섬을 확인해야 합니다. 공유·운영 DB의 migrate/repair는 이 작업에서 실행하지 않습니다.

실시간 가드의 프롬프트·모델·판정 기준과 팀원의 칸별 답변 처리, 출력 가드 거절 시 재시도 금지는 변경하지 않습니다. 실제 LLM/EC2 호출이나 운영 저장 부하 측정은 이번 가짜 응답 테스트에 포함하지 않습니다.
