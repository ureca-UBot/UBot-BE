# FAQ 검색 Threshold 테스트 보고서

2026-09-23

## 1. 테스트 목적

**기존 FAQ 중 어느 것과도 유사하지 않은 질문을 정확히 걸러내는 threshold를 찾는다.**

사용자 질문을 벡터로 변환해 Top-K(K=3)로 검색하고, 그중 threshold 이상인 결과만 사용한다. 검색 결과 각각은 독립적으로 자기 역할을 수행한다(일반=답변 반환, 매장검색관련=매장 서비스 호출, 사용자검색관련=사용자 서비스 호출). 여러 개가 동시에 살아남는 것 자체는 실패가 아니다 — 각 결과가 독립적으로 자기 역할만 정확히 수행하면 된다.

## 2. 지표

| 지표 | 정의 |
| --- | --- |
| 의도별 재현율(Recall) | 실제로 코퍼스에 유사한 FAQ가 있는 질문 중, 검색이 그걸 제대로 찾아낸 비율 |
| 무관 정확도 | 실제로 코퍼스에 유사한 FAQ가 하나도 없는 질문 중, 검색 결과가 정확히 빈 집합인 비율 |

## 3. 테스트 데이터

- **코퍼스**: 원본(불균형) 그대로, (질문, 권장 처리 의도) 2컬럼. 팀원 원본 FAQ 데이터를 그대로 사용. 의도 분포는 FAQ_RAG 983 / MAP_API 17 / USER_INFO 24이며, 인위적으로 균형을 맞추지 않았다. — FAQ가 아직 최종 확정되지 않았기 때문.
- **테스트셋**: 각 의도(일반/매장검색관련/사용자검색관련)에서 실제 존재하는 질문을 다양하게 샘플링하고, 오타 없이 자연스러운 표현 변형만 적용했다. 특정 어미(예: "궁금해요.", "부탁드려요.")에 몰리지 않도록 끝맺음을 다양화했다. 무관(코퍼스에 유사한 FAQ가 없는) 케이스도 포함했다.

## 4. threshold 스캔 결과

| threshold | 매장검색관련 재현율 | 사용자검색관련 재현율 | 무관 정확도 |
| --- | --- | --- | --- |
| 0.70 | 94.1% | 88.9% | 65.0% |
| **0.73 (1차 채택)** | **94.1%** | **88.9%** | **80.0%** |
| 0.745 | 94.1% | 87.5% | 83.0% |
| 0.775 | 90.2% | 80.6% | 90.0% |
| 0.795 | 86.3% | 77.8% | 92.0% |

일반 재현율은 threshold 전 구간에서 100%로 고정되어 트레이드오프에 영향을 주지 않는다.

## 5. 최종 채택안

0.70에서 0.73까지는 재현율 손실 없이 무관 정확도만 65.0%→80.0%로 오르는 구간이라 이 구간까지는 확실한 이득이다. 0.73을 넘어서면 재현율이 꺾이기 시작한다.

```
threshold = 0.73
일반 재현율: 100%
매장검색관련 재현율: 94.1%
사용자검색관련 재현율: 88.9%
무관 정확도: 80.0%
```

## 6. 임계값 선정 기준 (재사용 가능한 규칙)

1. **재현율을 먼저 확보한다.** 재현율이 꺾이기 시작하는 지점을 넘어서까지 threshold를 올리지 않는다.
2. **"공짜 구간"을 찾는다.** threshold를 올려도 재현율 손실 없이 무관 정확도만 오르는 구간이 있다면, 그 구간의 끝까지 올린다.
3. **공짜 구간이 끝나는 지점이 1차 후보다.** 그 지점을 넘어서면 재현율 손실이 무관 정확도 개선보다 커지므로 더 올리지 않는다.
4. **threshold를 올리고 내려도 특정 의도의 재현율이 계속 그대로라면, 그건 threshold 설정의 문제가 아니라 애초에 Top-K 안에 그 의도의 후보가 없다는 뜻이다.** `candidate-details` 파일에서 Top-K 안에 해당 의도 후보가 애초에 없는지 확인한다 — K값이나 코퍼스 구조의 문제이지 threshold로 해결되지 않는다.

### 6.1 규칙 4 상세 설명

**"threshold를 올리고 내려도 재현율이 계속 그대로"라는 말의 의미**

- 재현율: 특정 의도(일반/매장검색관련/사용자검색관련) 하나의 recall 수치
- threshold 구간: `THRESHOLD_CANDIDATES` 배열에 정의된 스캔 범위, 즉 0.700부터 0.795까지 0.005 단위로 찍은 모든 threshold 값들
- 전체에서 그대로: 그 구간의 모든 지점에서 숫자가 단 한 번도 바뀌지 않고 똑같다 — 딱 한두 지점만이 아니라

즉, threshold를 0.700 → 0.705 → 0.710 → ... → 0.795 로 하나씩 올려가며 특정 의도의 재현율을 찍어봤을 때, 그 값이 처음부터 끝까지 단 한 번도 바뀌지 않고 똑같은 숫자로 나온다는 뜻이다. 4절 표의 **일반 재현율**이 실제 예시다 — 0.70에서도, 0.73에서도, 0.795에서도 항상 100%로 고정되어 전 구간에서 변화가 없다. 반대로 매장검색관련은 0.70~0.745에서는 94.1%로 있다가 0.775에서 90.2%로 바뀐다 — 이건 재현율이 threshold에 따라 실제로 움직이는 정상적인 경우다.

**왜 이게 threshold 문제가 아니라는 신호가 되는가**

검색은 2단계로 이루어진다.

1. Top-K(K=3) 검색 — 코사인 유사도로 가장 가까운 후보 3개를 뽑는다 (threshold와 무관하게 항상 3개)
2. threshold 필터 — 그 3개 중 유사도가 threshold 이상인 것만 "생존"시켜 최종 결과로 삼는다

즉 threshold는 이미 뽑힌 Top-3 안에서 커트라인만 조정하는 역할이다. Top-3 안에 아예 들어오지 못한 후보는 threshold를 아무리 낮춰도 살아날 방법이 없다.

어떤 의도의 재현율이 스캔한 모든 threshold(0.70~0.795)에서 처음부터 끝까지 단 하나도 변하지 않는다면, 그 놓친 케이스들은 유사도 자체가 threshold 근처에 있는 게 아니라 애초에 Top-3 후보 목록에 그 의도가 존재하지 않는 경우일 가능성이 높다. 후보가 없으면 유사도 점수 자체가 없으니 threshold를 아무리 조정해도 결과가 달라질 수 없다.

**확인 방법**

`candidate-details` 파일에는 질문마다 실제 Top-3 후보와 각각의 의도·유사도가 그대로 찍혀 있다(`IntentClassificationAnalysis.java`의 `writeCandidateDetailsToFile`). 재현율이 안 움직이는 의도에서 놓친 질문들을 찾아, 그 질문의 Top-3 목록에 해당 의도 후보가 아예 있는지 없는지를 눈으로 확인하면 된다.

- Top-3 안에 그 의도 후보가 **있는데** 유사도가 threshold보다 낮아서 탈락 → threshold 문제. threshold를 낮추면 해결된다.
- Top-3 안에 그 의도 후보가 **아예 없음** (다른 의도 3개가 순위를 독차지) → threshold 문제가 아니다. K값을 늘려서 더 많은 후보를 봐야 하거나, 8절에서 언급한 것처럼 코퍼스 라벨링 자체가 애매한 경우(같은 주제가 여러 의도에 겹쳐 있는 경우)일 수 있다.

8절의 실제 사례가 이 두 번째 경우다: "저녁 늦게도 문 여는 매장이 있어요?"의 정답은 매장검색관련인데, Top-3가 전부 일반FAQ로 채워진 사례. 이건 threshold를 0.5로 낮춰도 해결되지 않는다 — 애초에 매장검색관련 후보가 Top-3 안에 없기 때문이다. 이런 케이스는 K를 3보다 늘리거나, "매장 영업시간"류 질문이 일반FAQ와 매장검색관련 양쪽에 중복 존재하는 코퍼스 구조 자체를 재검토해야 하는 문제다.

## 7. 재현 프로세스 (FAQ가 완성되면 이 순서로 다시 진행)

### 7.1 코퍼스 준비

1. 최신 FAQ 원본 파일(엑셀 등)에서 **질문**과 **권장 처리 의도**(FAQ_RAG/MAP_API/USER_INFO) 두 컬럼만 뽑는다. 질문 텍스트는 토씨 하나, 띄어쓰기 하나 바꾸지 않고 그대로 옮긴다 — 문구를 다듬거나 요약하면 실제 서비스와 다른 걸 테스트하게 된다.
2. 카테고리, 답변, ID 등 다른 컬럼은 전부 뺀다. 최종 코퍼스 CSV는 헤더 포함 딱 2컬럼(`질문`, `권장 처리 의도`)이어야 한다.
3. 의도값은 반드시 `FAQ_RAG` / `MAP_API` / `USER_INFO` 세 가지 문자열 그대로여야 한다 (Java 코드의 `INTENT_TO_GROUP` 매핑이 이 세 값만 인식한다). 다른 표기(예: "일반", "매장검색")가 섞여 있으면 실행 시 `IllegalStateException: 알 수 없는 의도값`으로 즉시 실패한다.
4. 의도 분포(각각 몇 개인지)를 세어서 기록해 둔다 — 나중에 결과를 해석할 때 "이 의도는 원본이 몇 개뿐이라 표본이 적다"는 걸 판단하는 데 필요하다.
5. 파일명은 `faq_intent_corpus.csv`로 저장한다.

### 7.2 테스트셋 준비

1. 코퍼스에 있는 실제 질문 중 각 의도(일반/매장검색관련/사용자검색관련)에서 여러 개를 무작위로 뽑는다. 의도당 개수는 그 의도의 원본 규모에 맞춘다 — 원본이 17개뿐인 의도를 100개로 억지로 늘리려 하지 않는다.
2. 뽑은 질문을 코퍼스 원문과 똑같이 두지 말고, 자연스러운 변형을 준다 (예: "~하십니까?"를 "~하세요?"로 바꾸는 정도의 구어체 변화).
3. 정답이 없는(코퍼스 어디에도 유사한 FAQ가 없는) "무관" 질문도 상당수 포함한다. 완전히 동떨어진 일상 주제와, 통신 서비스와 관련은 있지만 코퍼스에 실제로 없는 주제 두 종류를 섞는 것이 좋다.
4. 완성된 CSV는 헤더 포함 2컬럼(`질문`, `의도`)이어야 한다. 의도 컬럼 값은 `일반` / `매장검색관련` / `사용자검색관련` 중 하나이거나, 정답이 없으면 `무관`으로 적는다.
5. 파일명은 `intent_test_set.csv`로 저장한다.

### 7.4 실행 환경 준비 (Windows/PowerShell 기준)

콘솔 한글이 깨지는 걸 막기 위해, 새 PowerShell 창을 열 때마다 아래 세 줄을 먼저 실행한다.

```powershell
chcp 65001
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
$env:JAVA_TOOL_OPTIONS = "-Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8"
```

Docker의 Ollama 컨테이너가 떠 있는지 확인한다.

```powershell
docker ps
```

떠 있지 않다면 `docker compose up -d`로 실행한다.

### 7.5 테스트 실행

```powershell
.\gradlew.bat test --tests "com.ubot.embedding.analysis.IntentClassificationAnalysis" -i --rerun
```

`--rerun`을 반드시 붙인다 — 리소스 CSV만 교체했을 때 Gradle이 변경을 감지하지 못하고 이전 결과를 그대로 재사용하는 경우가 있었다.

실행이 끝나면 콘솔에 두 결과 파일의 경로가 출력된다.

```
build/reports/intent-analysis/candidate-details-YYYYMMDD-HHMMSS.txt   ← 질문별 Top-3 매칭 상세
build/reports/intent-analysis/summary-report-YYYYMMDD-HHMMSS.txt      ← threshold별 재현율·무관 정확도
```

두 파일 다 UTF-8로 저장되므로, 콘솔 인코딩과 무관하게 메모장이나 VS Code로 열면 항상 정상적으로 보인다.

### 7.6 threshold 스캔 결과 정리

`summary-report-*.txt`를 열어 threshold별로 다음을 표로 옮긴다.

| threshold | 일반 재현율 | 매장검색관련 재현율 | 사용자검색관련 재현율 | 무관 정확도 |
| --- | --- | --- | --- | --- |

기본 스캔 범위는 `IntentClassificationAnalysis.java`의 `THRESHOLD_CANDIDATES` 배열에 정의되어 있다(0.005 단위). 더 좁거나 넓은 구간을 보고 싶으면 이 배열 값만 바꾸면 되고, 다른 코드는 손댈 필요가 없다.

### 7.7 판단

6절의 규칙(재현율 우선 확보 → 공짜 구간 찾기 → 공짜 구간 끝을 1차 후보로)에 따라 threshold를 정한다.

### 7.8 상세 검증

어떤 의도의 재현율이 threshold 구간 전체에서 똑같은 값으로 고정되어 있다면, `candidate-details-*.txt`를 열어 그 의도의 놓친 질문들을 찾는다. (판단 근거는 6.1절 참고)

Top-3 안에 해당 의도 후보가 아예 없다면 (다른 의도가 순위를 독차지했다면) threshold를 아무리 조정해도 해결되지 않는다 — 8절의 구조적 한계에 해당하는지 확인하고, 필요하면 코퍼스 라벨을 재검토하거나 K값을 늘리는 것을 검토한다.

## 8. 구조적 한계

- **주제 경계가 모호한 FAQ 쌍**: 같은 주제(예: 매장 영업시간, 할인반환금)가 "일반FAQ"로도, "매장검색관련"/"사용자검색관련"으로도 코퍼스에 존재하면, 임베딩 유사도만으로는 구분이 안 되고 Top-K 경쟁에서 밀리는 경우가 생긴다. threshold 조정으로 해결되지 않으며, 코퍼스 라벨 재검토 또는 K값 증대가 필요하다. (실제 사례: "저녁 늦게도 문 여는 매장이 있어요?"가 정답인 매장검색관련 대신 "일반FAQ" 3개가 Top-3를 독차지한 경우를 확인함.)
- **K=3의 한계**: Top-K 후보가 특정 의도로 쏠리면, 실제로 유사한 다른 의도의 FAQ가 있어도 순위 밖으로 밀릴 수 있다.

## 9. 남은 과제

1. **FAQ 최종 확정 후 전체 재실행 필요**: 지금 결과는 전부 미확정 코퍼스 기준이며, 5절의 수치는 참고용일 뿐 최종값이 아니다.
2. **운영 코드 반영**: `ChatService`의 `CONFIDENCE_THRESHOLD` 상수는 이번 결과를 반영해 LLM 팀과 함께 갱신해야 한다.
3. **FAQ 카테고리 → 3분류 매핑 코드 필요**: 운영 `Faq` 엔티티에는 아직 일반/매장검색관련/사용자검색관련 구분 필드가 없다. 카테고리 매핑 로직 또는 신규 필드 추가가 필요하다.

## 10. 사용 파일

- `faq_intent_corpus.csv` (원본 2컬럼: 질문, 권장 처리 의도)
- `intent_test_set.csv` (어미 다양화·문법 수정 최종본)
- `IntentClassificationAnalysis.java` (Top-K 통합 검색, 재현율·무관 정확도 산출, 결과 파일 자동 저장)
- `build/reports/intent-analysis`에 `candidate-details-YYYYMMDD-HHMMSS.txt`, `summary-report-YYYYMMDD-HHMMSS.txt`가 타임스탬프 별로 저장된다.
