# 실패와 과부하 시 동작

UBot-BE는 모든 의존성이 항상 정상이라고 가정하지 않습니다. 질문 작업은 PostgreSQL에 남기고 Redis는 Worker를 깨우는 신호로 사용하며, 실행 소유권과 제한 시간을 DB 상태로 판정합니다.

## 지켜야 하는 불변식

1. `chat_jobs`와 연결된 답변 시도 기록이 작업 상태와 최종 결과의 원본입니다.
2. Redis 메시지는 DB 커밋 뒤에 발행하고, Worker는 결과 DB 커밋 뒤에 ACK합니다.
3. `started_at` 실행 토큰이 현재 실행과 일치할 때만 heartbeat·성공·실패를 기록합니다. 회수된 이전 실행의 늦은 결과는 버립니다.
4. 회원은 JWT 사용자, 게스트는 서버 세션의 대화로 작업 소유권을 확인합니다. 없는 작업과 다른 사용자의 작업은 같은 오류로 처리합니다.
5. 모델 재시도와 Worker 회수는 접수 후 전체 기한과 한 실행의 제한을 연장하지 않습니다.
6. 모델이 제안한 가입·예약·변경은 곧바로 상태 변경이 되지 않습니다. 인증·소유권을 확인하는 서버 API가 실제 변경을 수행합니다.

세부 구현과 테스트는 [Worker 장애 복구](how-to/worker-reliability.md)에서 확인합니다.

## 장애 분류

| 조건 | 감지 신호 | 시스템 동작 | 복구 기준 | 호출자 행동 |
|---|---|---|---|---|
| API 중단 | `up{job="ubot-backend"} == 0`, Nginx 502 | 새 요청을 받지 못함. 이미 Worker가 실행 중인 작업은 계속될 수 있음 | Backend health와 공개 API가 정상 | 새 질문을 중복 제출하지 말고 백오프 후 재시도 |
| PostgreSQL 중단·고갈 | `pg_up == 0`, Hikari pending 증가, SQL 오류 | 접수·인증·저장이 실패. 작업 조회는 기본 1.5초 예산 안에서 `503 CHAT-025`. Worker는 결과를 ACK하지 않음 | DB 연결 복구, pending 감소, 기존·신규 작업 조회 성공 | 조회는 백오프하고 접수 결과를 받았다면 같은 질문을 새로 보내지 않음 |
| Redis 중단·유실 | `redis_up == 0`, 스트림 발행·읽기 오류 | DB에 접수된 작업은 유지. 복구 뒤 미발행 작업을 DB 기준으로 다시 발행. 로그인 제한·토큰 폐기 조회·회원 rate limit은 해당 경로의 정책에 따라 제한적으로 fail-open | Redis 연결과 스트림 소비 복구, DB 대기 작업 감소 | 작업 조회를 계속하되 5xx에는 백오프. 인증 보안 기능의 저하를 운영자가 확인 |
| Worker 중단 | `chat_worker_ready == 0`, queue age 증가 | API는 `202`로 접수할 수 있으나 답변 처리가 지연. heartbeat가 끊긴 실행은 다른 Worker가 회수 | Worker ready, 최장 대기 시간 감소, 테스트 작업 완료 | 화면은 처리 중 상태를 유지하고 접수 후 전체 기한까지 조회 |
| vLLM 연결 실패·5xx | 모델 오류와 재시도 로그, `WAITING_FOR_MODEL` | Worker가 기본 5초 간격으로 같은 실행을 재시도. FAQ 검색·도구 결과는 다시 만들지 않음 | 모델 응답 후 같은 작업이 성공하거나 실행 기한 종료 | 새 질문을 만들지 않고 작업 상태를 조회 |
| 모델 4xx·잘못된 응답·HTTP timeout | LLM 오류 코드, 작업 `FAILED` | 자동 연결 재시도를 적용하지 않고 오류로 확정. 형식 오류의 일부 도구 경로만 정해진 1회 복구를 수행 | 설정·프롬프트·모델 호환성을 고친 새 시도 성공 | `retryable`과 오류 코드를 확인해 사용자 재시도 또는 운영 문의 |
| 임베딩 서버 실패 | `EM-*`, 임베딩 지연·실패 지표 | 자동으로 다른 Provider로 바꾸지 않음. 검색 근거를 만들 수 없는 작업은 실패 | 같은 Profile의 서버 복구와 백필 상태 확인 | 확정 실패 뒤에만 재시도 |
| 외부 지도 API 실패 | 위치·길찾기 오류 코드 | 해당 위치·경로 기능을 실패 처리하며 저장된 데이터를 임의로 보충하지 않음 | 외부 API·키·쿼터 정상화 | 입력과 오류 코드를 확인하고 나중에 다시 시도 |

각 장애의 확인·조치·금지 작업은 [런북](runbooks/README.md)에 있습니다.

## 제한 시간과 재시도

| 경계 | 기본값 | 의미 |
|---|---:|---|
| 작업 조회 예산 | 1.5초 | 인증 사용자 조회·게스트 승계·작업 조회가 공유. 초과·실행 용량 소진·DB 오류는 `CHAT-025` |
| 작업 조회 동시 실행 | 8 | 취소에 즉시 반응하지 않는 JDBC 조회까지 포함. 넘치면 별도 대기열 없이 거절 |
| 접수 후 전체 대기 | 10분 | 이 안에 실행·회수를 마치지 못하면 `CHAT-016` |
| 한 실행 | 180초 | 임베딩·도구·모델 복구 대기를 포함하며 단계·재시도로 연장하지 않음 |
| 모델 연결 재시도 간격 | 5초 | Worker 안의 vLLM 연결 실패·5xx에만 적용 |
| Worker heartbeat timeout | 1분 | heartbeat가 끊긴 실행을 회수할 수 있는 기준 |
| Worker 강제 회수 idle | 5분 | 메시지가 오래 ACK되지 않은 경우의 마지막 안전망 |
| Worker 최대 전달 | 3회 | 소진하면 `CHAT-015`로 종료 |

실제 값은 [설정 Reference](reference/configuration.md)와 실행 환경변수를 기준으로 합니다.

## 과부하

```text
정상 → 실행 슬롯 포화 → 대기열 증가 → 요청 제한·시간 만료 → 복구
```

| 압력 지점 | 제한 | 초과 동작 | 확인 신호 |
|---|---|---|---|
| 회원 질문 접수 | 기본 60초에 30건 | 새 작업을 만들지 않고 `429 CHAT-026` | rate limit 로그·응답 코드 |
| 게스트 질문 | Nginx IP 제한과 DB 질문 횟수 | 429 또는 `CHAT-017` | Nginx 로그·게스트 설정 |
| Worker 실행 | 프로세스별 기본 4개 | 슬롯이 생길 때까지 Redis 메시지를 더 읽지 않음 | `chat_worker_active`, queue age |
| LLM 호출 | 기본 Worker 동시 실행 수와 동일 | 허가가 생길 때까지 대기하며 취소·마감을 확인 | LLM 포화도·지연 |
| 작업 조회 | 기본 8개, 요청별 1.5초 | `503 CHAT-025` | 조회 실패 로그와 Hikari pending |
| 상담 메시지 | 기본 60초에 30건 | 상담 rate limit 오류 | 상담 오류 코드·로그 |

클라이언트는 작업 조회를 1~2초 간격으로 시작하고 429·5xx·네트워크 오류에는 지수 백오프와 jitter를 적용합니다. 성공·실패·취소가 확정되면 조회를 멈춥니다.

## 복구의 한계

- 인터럽트를 무시한 외부 호출은 Worker 슬롯을 반환한 뒤에도 원격에서 계속 계산할 수 있습니다. 늦게 온 결과는 저장하지 않지만 원격 계산 자체를 취소한다고 보장하지 않습니다.
- 게스트 세션은 API 메모리에 있으므로 세션 만료·API 재시작 뒤 과거 게스트 작업 조회 권한을 잃을 수 있습니다.
- Redis가 복구돼도 최근 스트림 데이터가 볼륨에 남았다고 가정하지 않습니다. DB 대기 작업 재발행으로 수렴합니다.
- Flyway를 되돌리는 자동 경로는 없습니다. 스키마 변경이 포함된 배포는 이미지 롤백만으로 원상 복구되지 않을 수 있습니다.
- 실제 처리량과 복구 시간은 GPU·DB·네트워크·데이터 규모에 따라 달라집니다. 저장된 측정 결과는 [장애 검증 기록](evidence/fault-recovery-20261023.md)의 조건에서만 해석합니다.
